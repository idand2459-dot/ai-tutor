## Goal
Build the first version of `frontend/`: a single-page Next.js `chat` where the user sends a
`message`, sees the `tutor` reply stream in as it is generated, and gets a clear `sonner` toast
when anything fails, with the `chat` and the typed input left intact. The UI uses the existing
`proxy` contract in `.doc/architecture.md` (plan 001) exactly as written. It proves AC02, AC03,
and AC06, and the frontend part of AC01, with Vitest component tests (see Q4).

## Scope
In scope:
- Set up the `frontend/` package: Next.js 16 (App Router), React 19, TypeScript, Tailwind CSS v4,
  `@tailwindcss/typography`, `sonner`, `lucide-react`, ESLint, and Vitest + React Testing Library + jsdom.
- `frontend/.env.example` with `NEXT_PUBLIC_PROXY_URL=http://127.0.0.1:4000`, created right
  after create-next-app runs (Step 2).
- A chat client that sends `POST {NEXT_PUBLIC_PROXY_URL}/api/chat` with
  `{ messages: [{ role: "user" | "tutor", content }] }` and reads the SSE stream from the
  response (`delta` / `done` / `error`).
- A message list that shows `user` and `tutor` messages, with an empty-state prompt and
  auto-scroll to the newest `message`.
- The streaming display: each `delta.text` is appended, in order, to the last `tutor` message.
- A loading state: an indicator appears as soon as the user sends and stays until `done` or
  `error`. The send button is disabled the whole time. The textarea stays editable.
- Error handling for every contract code (`validation_error`, `upstream_rate_limited`,
  `proxy_misconfigured`, `upstream_unavailable`, `tutor_refused`, `internal_error`), plus a
  network failure, an unknown code, a non-JSON error body, and a stream that ends without
  `done` or `error`. Each one shows one `sonner` toast and leaves the `chat` and the typed
  input intact.
- `tutor` messages render as Markdown (`react-markdown` + `remark-gfm`), with fenced code in
  `<pre><code>` blocks styled by `@tailwindcss/typography`, and never through
  `dangerouslySetInnerHTML`. `user` messages render as plain text.
- Client-side limits that match the `proxy`: a request has at most 49 `message` items, and each
  `content` is at most 8,000 characters and non-empty after trimming.
- Unit and component tests in `frontend/tests/unit/` (see Validation).
- Docs: `.doc/architecture.md` (frontend components, data flow, env var) and a short
  `frontend/README.md`.

Out of scope:
- Any change to `backend/` or to the API contract.
- The "Generate Quiz" button, `/api/quiz`, and AC04 / AC07 (next backlog task, `stack:full`).
- Saving the `chat` between page loads (no `localStorage`, no database), accounts, and deployment.
- A "stop generating" button (Q5).
- Syntax highlighting in code blocks (`rehype-highlight` + a highlight.js theme). It is a later
  addition (Q3).
- E2E tests (Playwright) and a stub `proxy`. They are a later addition (Q4).
- Automatic retries in the browser. The user resends by hand (the input is restored).
- Figma: the backlog item has no `figma:` reference. The layout is a plain single column.
- Updating `.claude/agents/frontend.md` is deferred until the lesson on parallel agents.

## Assumptions
- The contract in `.doc/architecture.md` → `## API Contract` is final. This plan does not change
  it, and there is no `.orchestrate/api-contract.yaml` (plan 001, Q6).
- The browser talks only to the `proxy`. Next.js has no API routes and no server-side fetch
  in this task, so the browser makes all requests to the `proxy` directly, and CORS on the
  `proxy` (`FRONTEND_URL`) is what allows them.
- **Security check for `NEXT_PUBLIC_PROXY_URL`.** AGENTS.md forbids two things: the
  `NEXT_PUBLIC_` prefix *on `ANTHROPIC_API_KEY`*, and any reference to the key from `frontend/`.
  The `proxy` URL is not a secret. Next.js inlines it into the client bundle at build time, and
  that is the intended behavior. So there is no conflict with the Security rule. The only rule
  is that `NEXT_PUBLIC_*` must never hold a secret; Step 2 adds a comment to `.env.example` that
  says so.
- Env files: the `block-secret-file-access` hook blocks Claude Code from reading or writing
  `frontend/.env`, `.env.local`, `.env.development`, and `.env.production`. Only
  `frontend/.env.example` is used. The code falls back to `http://127.0.0.1:4000` when the
  variable is unset, so local development needs no env file at all.
- CORS matches the origin exactly. The backend's `FRONTEND_URL` is `http://localhost:3000`
  (`backend/.env.example`), so the app must be opened at `http://localhost:3000`, not
  `http://127.0.0.1:3000`.
- The `chat` lives only in React state for the page's lifetime (product scope: no persistence).
  The full history is sent on every request, because the `proxy` is stateless.
- Each `message` in the UI has a client-only `id` (`crypto.randomUUID()`) for React keys. The
  request body sends only `role` and `content`.
- The limits come from the contract: a valid request has an odd number of `message` items and
  at most 49. Sending is allowed only while the `chat` has at most 48 messages, which is 24 full
  exchanges. After that, the input is disabled and an inline notice says the `chat` is full and
  the page must be reloaded to start a new `chat`. A "new chat" button is not part of V1.
- Work happens on the existing `feat/chat-ui` branch. It was created from `main` at `6880f1e`
  and has no commits of its own yet.
- Single-session workflow, like plan 001: one Claude Code session does every step.

   Answer: As recommended, with one fix. create-next-app refuses a non-empty target directory,
   so `frontend/.env.example` is created right after create-next-app runs (Step 2), not before.

2. **Reading SSE from a POST.** `EventSource` only supports GET, so it can't send the `chat` body.
   Recommended: `fetch` with `AbortController`, then
   `response.body.pipeThrough(new TextDecoderStream()).pipeThrough(new EventSourceParserStream())`
   from the small, dependency-free `eventsource-parser` package. It handles events split across
   chunks, CRLF line endings, and multi-line `data`. `chat.client.ts` turns the parsed events
   into typed `delta` / `done` / `error` values. Rules:
   - A non-2xx response is read as JSON in the standard error shape. If the body isn't valid
     JSON, the client reports `internal_error`.
   - A 2xx response without `text/event-stream` is treated as `internal_error`.
   - A stream that closes without `done` or `error` is treated as `upstream_unavailable`.
   - A `fetch` rejection (proxy down, or blocked by CORS) is a separate `network_error`, which
     exists only on the client and is not a contract code.
   Not recommended: `@microsoft/fetch-event-source`, which retries automatically by default
   (the error-handling skill says not to retry this kind of error) and is barely maintained.
   Answer: As recommended.

3. **Markdown library.** Recommended: `react-markdown` + `remark-gfm` + `rehype-highlight`, with a
   highlight.js theme `@import`ed in `globals.css`.
   Answer: `react-markdown` + `remark-gfm` + `@tailwindcss/typography` only. No
   `rehype-highlight` and no highlight.js theme in V1; syntax highlighting is a later addition.
   These rules stay:
   - `react-markdown` builds React elements and never uses `dangerouslySetInnerHTML`. It
     ignores raw HTML unless `rehype-raw` is added, and that package must not be added.
   - Disallow `img` (`disallowedElements={["img"]}`). The `tutor` output is untrusted, and an
     image would make the browser call a third-party host, which breaks the AC06 rule that the
     browser calls only the `proxy`.
   - Links: keep the default `urlTransform` (it blocks `javascript:` URLs) and add
     `target="_blank" rel="noopener noreferrer"`.
   - Prose and code blocks are styled with the typography plugin's `prose` classes
     (`@plugin "@tailwindcss/typography"` in `globals.css`).

4. **Test tooling.** Recommended: Vitest + React Testing Library for unit tests, and Playwright
   against a gated stub `proxy` for e2e.
   Answer: Vitest + React Testing Library + jsdom only (`globals: false`). No Playwright, no stub
   `proxy`, no `tests/e2e/`, and no `test:e2e` script.
   - Tests of the SSE logic alone run in the `node` environment (`// @vitest-environment node`)
     on real `ReadableStream` objects.
   - AC02 and AC03 are proved by a component-level test of `ChatView`
     (`tests/unit/chat-view.test.tsx`). It mocks the global `fetch` to return a `Response` whose
     body is a `ReadableStream` the test controls, and the test enqueues each SSE chunk by
     hand. A small helper, `tests/unit/helpers/controlled-sse-response.ts`, returns the
     `Response` plus `push(eventText)`, `close()`, and `error()`. Chunks are released only when
     the test asks, so there is no timing flakiness.
   - AC06's browser-network check becomes a unit test asserting that every `fetch` call goes
     to `PROXY_URL` only. The grep checks and the manual smoke step stay.

5. **"Stop generating" in V1?** Recommended: **no**. Even so, the hook keeps an `AbortController`
   and aborts the request when the component unmounts, so the `proxy` aborts the upstream call
   (plan 001, step 8). A stop button means deciding what to do with a half-finished reply, and
   it adds tests. It can come later, using the same `AbortController`.
   Answer: As recommended.

6. **What happens to a failed exchange?** The rule says "keep the chat and the typed input
   intact". Recommended: on **any** failure (before the stream, mid-stream, or `tutor_refused`),
   remove the unanswered `user` message and the partial `tutor` message, and put the user's
   text back into the input, unless the user has already typed something new; in that case,
   keep the new text. The `chat` is then exactly what it was before sending, and it still
   alternates roles, so the next request is valid. Alternative: keep a partial `tutor` reply
   marked "interrupted". That is more state, and its partial text would be sent to the model as
   if it were a full reply.
   Answer: As recommended.

7. **Toast text per error code.** Recommended (short, with a recovery hint, per the error-handling skill):

   | Code | Toast |
   |---|---|
   | `validation_error` | "Message couldn't be sent. Check its length and try again." |
   | `upstream_rate_limited` | "The tutor is busy. Wait a moment, then send again." |
   | `proxy_misconfigured` | "The proxy isn't set up correctly. Check the backend API key and model." |
   | `upstream_unavailable` | "The tutor is unreachable right now. Send again in a moment." |
   | `tutor_refused` | "The tutor declined to answer. Try rephrasing your message." |
   | `internal_error` | "The proxy hit an unexpected error. Send again." |
   | `network_error` (client only) | "Can't reach the proxy. Is the backend running on port 4000?" |
   | unknown code | Same as `internal_error`. |

   The server's `error.message` is not shown. The text comes from this table only, so it is
   stable and testable. The `requestId` goes in the toast description in small text, to help
   match the toast to a backend log line.
   Answer: As recommended.

## Risks
- **AC06 coverage is narrower.** The unit test sees only `fetch` calls, not every request the
  browser makes. Mitigation: the `img` block in Markdown, the grep checks, and no other
  network code in `frontend/src`.
- **Web streams in jsdom.** If the jsdom environment lacks `Response`, `ReadableStream`, or
  `TextDecoderStream`, the `ChatView` tests can't run. Mitigation: the Step 3 smoke test fails
  early, and the fallback is to import them from `node:stream/web` in `vitest.setup.ts`.
- **CORS origin mismatch.** Opening the app at `127.0.0.1:3000` while `FRONTEND_URL` is
  `localhost:3000` makes every request fail, and it looks like a network error. Mitigation:
  `frontend/README.md` says to use `localhost`, and the `network_error` toast names the proxy.
- **Markdown during streaming.** An unclosed code fence renders oddly until it closes. This
  doesn't affect correctness. Re-parsing the whole reply on every `delta` is fine for 4,096
  output tokens.
- **Next.js 16 / Tailwind v4 / ESLint versions** installed by create-next-app may differ from
  what this plan expects (for example, `next lint` has been removed). Mitigation: Step 2 keeps
  what create-next-app installs and checks it before any feature work.
- **Mid-stream `upstream_unavailable` after a long reply** discards the text the user already
  saw (Q6). This is accepted for V1. The input is restored, so resending costs one click.
